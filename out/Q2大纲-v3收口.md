# Q2 大纲 · v3（收口：五处可执行化 + 一处预案）

> v1 是骨架，v2 是七处批判。**v3 只做两件事**：把 v2 的模糊处变成可操作判据，并补一个 v2 完全没有的东西——**输了怎么办**。

---

## 1. X/Y 分类的可操作判据

**v2 说**：「35 项里有 X 项满足『有构造样本 + 变异测试敏感』，Y 项只是有判据。」

**但那不可操作。** 判据要能用一条命令跑出来：

| 类别 | 判据（可机械查） | 怎么查 |
|---|---|---|
| **X（强）** | 该门在 `fence_acceptance.py` 的样本里出现过 **且** 在 `fence_mutation.py` 的变异列表里 | grep 两个脚本 |
| **Y（弱）** | 只在 `gate.py` 里有实现，没有独立样本 | 差集 |
| **Z（不算门）** | 只是「打印一行」，不做判定 | 人工 |

**预期**（凭记忆，需实测）：`fence_acceptance` 有 S1–S12 共 12 个样本，`fence_mutation` 有 4 个变异。
**所以 X 最多 4–12 项，Y 会是 20+ 项。**

**这个结果会很不好看，但它必须报。** 报法的正确形式：

> 35 道门里，**X 项有构造样本且经变异测试验证**，**Y 项有判据但没有独立样本**，**Z 项不计**。
> 我们不把 Y 项算作「已验证」——**它们只是「有代码」。**

**这一句话比「35 项全绿」诚实一百倍，而且审稿人会因此信剩下的部分。**

## 2. 「增量检出」的正确算法

**v2 说**：「C2 能抓『有等式无证明』，C3 能抓『无过程记录』。」

**但那只是「门能抓」，不是「增量」。** 增量必须定义成：

```
增量(L2) = 在 C1 条件下漏检、在 C2 条件下检出的构造缺陷数
增量(L3) = 在 C2 条件下漏检、在 C3 条件下检出的构造缺陷数
```

**操作上**：

| 条件 | 跑什么 | 记录 |
|---|---|---|
| C1 | `gate --only numbers` | 构造样本 S_L2（删掉证明）、S_L3（删掉迭代表）是否被检出 |
| C2 | `gate --only numbers,proof` | 同上 |
| C3 | `gate --only numbers,proof,iterlog` | 同上 |

**关键**：**S_L2 和 S_L3 是「同一篇论文的两个变体」**——只删一处，其它不动。**这样增量才是干净的。**

**如果 C1 就能检出 S_L2**（比如 `numbers` 门恰好因为别的原因报错），那说明**样本设计失败，要重做**。

## 3. 判断「能不能过 Q2」的最小集：三项，不是四项

**v2 说「前四项 2 天」，但第 4 项（核心图）是写作，不是判断。**

**真正决定能不能过的只有三项**：

| # | 判什么 | 通过线 | 不通过怎么办 |
|---|---|---|---|
| **1** | **35 项的 X/Y** | **X ≥ 8** | 若 X < 8，说明大部分门没有独立验证，**先补样本，别写论文** |
| **2** | **逐层消融的增量** | **增量(L2) ≥ 1 且 增量(L3) ≥ 1** | 若为 0，**三层叙事塌了**，改成「两层」或「一个工具」 |
| **3** | **FActScore 的四种结果** | 出现「unsupported」「跑不起来」「无判断」任一 | 见下节预案 |

**三项合计 1.5 天。做完就能决定：投 Q2、降 Q3、还是回头补实验。**

## 4. 预案：如果 FActScore 让我们输

**这是 v2 完全没有的东西。**

### 情形 A：FActScore 判 `R²=0.94` 为 **unsupported**

**我们赢。** 这是最理想结果：它把「计算出来的数」判成「无依据」。
**论文的立论成立**：现有评测混淆了「事实错误」与「来源不同」。

### 情形 B：判为 **supported**，且理由是「它引用了某个真实数据集的 R²」

**我们输一半。** 说明那个 R² **确实**能被知识源支持（可能是一个公开数据集上的已知结果）。

**应对**：**把主张收窄到「无法被任何公开知识源支持的计算值」**。
**操作**：在 23 篇里筛出「冻结表里有、但语料里找不到来源」的子集，只在这个子集上立论。
**这个子集有多大，是可以测的**——`freeze` 已经有 `generated_from`，能追到脚本。

### 情形 C：判为 **supported**，但它其实是**凭先验猜的**

**这是最危险的情形，也是我们最想抓的。**

**检测方法**（v2 第 3 条提过，这里给操作）：
把 `R²=0.94` 改成 **`R²=0.9999997`**（荒谬值），再跑一次。
- **仍判 supported** → **它看形状不看内容**，我们抓到一个真缺陷
- **改判 unsupported** → 它在读数值，**那情形 B 或 A**

**这个「荒谬值测试」是关键实验**，成本几乎为零（改一个数重跑）。

### 情形 D：FActScore 跑不起来

**不是我们的错，但也不能当证据。**

**应对**：**只报「它依赖 LLM + 知识源，我们不满足条件」，不报「它不行」**。
**并把 baseline 换成可跑的**：`pytest --doctest-modules`（能跑）+ 手工核对（`grade.py` 的 23 项判据可以当「人工基线的机械化版」）。

## 6. v3 之后还剩什么没解决

| 未解决 | 为什么 |
|---|---|
| **「分类器会被绕过」没有量化** | v2 提了「要测漏检率」，但**没有实验设计**。这是最大的残余风险 |
| **七类自欺的分类是否完备** | 这是「我们想到的七类」，**不是「所有类」**。审稿人会问「第八类是什么」 |
| **`proof` 门的判据是否过松** | 「≥60 有效字符」是**任意阈值**，**没有依据** |
| **迭代史的「不信判据词表」是人工定的** | 中英两套词表，**词表外的诚实记录会被漏检** |

**这四条都应该写进 Threats，而不是假装解决了。**

**其中第一条（分类器漏检率）有实验设计**：

> 构造 N 个「长得像结构值、实际是计算值」的样本（如把 `0.5` 写成 `500000` 的整数形式，或把计算值写成 `1e6` 的科学计数法），
> 跑 `untraced.classify_token`，**报漏检率**。
> **这是把「已知局限」变成「已量化局限」的唯一办法。**
