## 0. 数字口径说明（先说在前）

**本文用了三处「估计值」，不是精确计数**：

| 数字 | 怎么来的 | 精度 |
|---|---|---|
| heredoc 吞引号「≥ 5 次」 | 从对话里回数的**估计** | 量级正确，具体值可能差 1–2 |
| 检测器自错「6 次」 | 同上 | 同上 |
| 页数「34→31→31→30」 | 每次编译后的实测输出 | **精确** |

**为什么不能精确**：本会话 session_event_search 超时（30 秒未返回），无法对历史事件做全文计数。

**这个口径问题本身就是 L2 的反例**：一个有记录（L3 高）的过程，如果记录里的数字是估的，读者仍然无法核对。**所以论文里如果要报这类计数，必须用可复现的来源（如 
un_all 的日志行数、git log 的 commit 数），不能用回数。**

## 1. 四层独立性：三组证据

**判据**：「独立」= 存在实例，其中一层失败而其余层不失败。

### 证据 A：A 臂 —— L1 高、L2 低

| 层 | 状态 | 证据 |
|---|---|---|
| **L1** | ✅ **199/199** 全 token 可溯源；冻结表 818 条 | `verify.py` 实测 |
| **L2** | ❌ **无命题无证明** | 外部评审原话：「用可检查的等式替代了证明」 |
| L3 | ✅ 6 轮迭代表 | R124 新增 |
| L4 | 未测 | — |

**这一条证明 L1 与 L2 独立**：数字全对，推导可以是空壳。

### 证据 B：B 臂 —— L1 低、L2 高

| 层 | 状态 | 证据 |
|---|---|---|
| **L1** | ❌ **无冻结表**；200 个小数只能人工核对 | 目录扫描 |
| **L2** | ✅ **命题 + 完整证明**（内层逐分量可分、乘子在双范数饱和） | 论文 §5.2 |
| L3 | ✅ 五轮迭代史 | `PROCESS_SUMMARY.md` |
| L4 | ✅ 26 分 25 秒完成 | 耗时表 |

**这一条反向证明 L1 与 L2 独立**：有证明，但数字不可机械核。

### 证据 C：**本次会话 —— L3 高、L4 低**

**这是最硬的一条，因为它是真实的、不是构造的。**

| 层 | 状态 | 证据 |
|---|---|---|
| **L3** | ✅ **高** | 写了 `HANDOFF.md`、`CHANGELOG.md`（R121–R124 逐轮）、`tab:iterlog`（6 轮，含「不信判据」） |
| **L4** | ❌ **低** | **见下表**——同一个坑反复踩，且每次都「再试一次」而不是换方法 |

**L4 的实测清单（这一整轮会话）**：

| 坑 | 踩了几次 | 每次的处理 |
|---|---|---|
| **PowerShell heredoc 吞引号/转义** | **≥ 5 次** | 每次都是「换个写法再试」，第 5 次才改用「写临时 .py 文件」 |
| **`[IO.File]::WriteAllLines` 写 CRLF** | **2 次** | 第二次才想起用 `WriteAllText` |
| **`Test-Path` 中文路径报错** | 1 次（刷了 40 行错误） | 改成 python 读 |
| **检测器自己出错** | **6 次**（`fig_visual` ×2、`roster`、`triage`、`numeric_genre`、`chk_` 计数） | 每次都「修检测器再跑」，没有一次先怀疑流程 |
| **页数超 30** | **4 次**（34→31→31→30） | 每次收一点边距/图宽，没有一次直接算「需要压几页」 |
| **`$git:` 被当驱动器** | 1 次 | — |

**结论**：

> **L3 满分的报告，可以同时 L4 崩到反复踩同一个坑。**
> **因为 L3 查的是「有没有记录」，L4 查的是「当下是不是在打转」。**
> **我记录了（HANDOFF/CHANGELOG/iterlog），但记录里写的正是「我又踩了一次」。**

**这一条是论文里最诚实的例子，也是最有说服力的**——它来自作者自己的失败，不是构造的样本。

### 独立性总结

| 对 | 有实例吗 | 来源 |
|---|---|---|
| L1 × L2 | ✅ 双向（A 臂、B 臂） | A/B 实测 |
| L1 × L3 | ⚠️ 弱（B 臂 L1 低 L3 高；A 臂 L1 高 L3 高） | A/B |
| L2 × L3 | ⚠️ 弱（A 臂 L2 低 L3 高） | A/B |
| **L3 × L4** | ✅ **单向强**（本次会话） | **真实** |
| L1 × L4 | **不需实例** | **类型独立**：L1 查静态产出，L4 查运行轨迹，对象不重叠 |
| L2 × L4 | **不需实例** | 同上 |

**所以要补的不是实例，是「可观测性」**：L4 的信号（同错计数、编辑距离、上下文占比）必须实现，否则「L4 低」只可事后推断、不可实时发现。

## 2. 元层为什么是「过程不发散」，不是别的

**候选的元层，逐个对比**：

| 候选 | 问的问题 | 可机械判 | 为什么不是它 |
|---|---|---|---|
| **成本控制** | 花了多少 token | ✅ | **它是约束，不是判据**——花得多不一定不对 |
| **人工干预** | 什么时候该问人 | ⚠️ 部分 | 「该问」本身要判断，是元-元层 |
| **任务分解** | 该不该拆 | ❌ | 拆得对不对要试了才知道 |
| **过程不发散** | 现在是在解决还是在打转 | ✅ | **✅ 选它** |

**为什么「过程不发散」能胜出**：

1. **信号全是过程量**（失败次数、编辑距离、上下文占比）——**不是结果量**，所以不会被奖励劫持
2. **它判的是「继续有无意义」**，不是「内容对不对」——**与 L1–L3 的对象不同**
3. **它可实时**，而 L1–L3 都可以事后
4. **它的失败有可观测的代价**：这一整轮会话就是证据

**关键区分（必须写进论文）**：

> **L4 调的是「投入门槛」，不是「质量门槛」。**
> 降投入（早停、换法）✅ ／ 降质量（接受更差结果）❌

**因为降质量的终点是「把做不出来写成做到了」，而那是这个项目全程在防的事。**

## 4. 核心图设计（文字版，不画）

**Q2 需要一张「一图说清全文」的图。** 建议这样：

```
┌─────────────────────────────────────────────────────────┐
│  内容层（产出对不对）                                    │
│                                                         │
│   L1 值        L2 推导        L3 过程                    │
│   ┌────┐      ┌────┐        ┌────┐                      │
│   │一个数│     │一条推理│     │一次迭代│                  │
│   └────┘      └────┘        └────┘                      │
│   判据：       判据：         判据：                      │
│   在冻结表里？  有非空证明？    有不信判据？                │
│   ─────────────────────────────────────                  │
│   失败：       失败：         失败：                      │
│   数字是编的    有等式无证明   事后复盘代替当下怀疑         │
│                                                         │
│   实测独立性：A 臂 199/199 但无证明；B 臂有证明但无冻结表     │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  元层（继续有没有意义）                                   │
│                                                         │
│   L4 过程不发散                                          │
│   判据：连续同错 3 次？上下文 > 70%？编辑距离趋零？          │
│   动作：换方法 / 停 / 压缩上下文  ← 调投入，不调质量        │
│                                                         │
│   实测：本次会话 L3 满分（HANDOFF+CHANGELOG+iterlog），     │
│         L4 崩（heredoc 踩 5 次、检测器自错 6 次）          │
└─────────────────────────────────────────────────────────┘
```

**这张图的三条设计原则**：

1. **左边写「对象」，右边写「判据」**——读者先看到「查什么」，再看到「怎么查」
2. **每层配一个「失败的表现」**——这比「判据」更让人记住
3. **底部一行实测量**——不是「我说它独立」，是「A 臂 199/199 但无证明」

**不要画的元素**：箭头表示「层次递进」（会误导成「上一层包含下一层」——它们是并列的对象，不是嵌套）。
